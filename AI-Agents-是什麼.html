01 · 定義

什麼是 AI Agent？

  • 經典定義：Agent 是任何能透過感測器感知環境、並透過致動器對環境採取行動的東西。 S14
  • LLM Agent：由 LLM 動態主導自己的流程與工具使用，自己決定如何完成任務。 S1
💡 關鍵字：自己決定流程與工具 —— 這是 Agent 和一般程式最大的不同。
📖 Wiki 出處：definition.md › 重點 1、2

01 · 定義

Agent、聊天機器人、Workflow 差在哪？

  • 與 Workflow 的差別：Workflow 是由程式碼預先寫好路徑來串接 LLM 與工具；Agent 則是由模型在執行中決定下一步。 S1
  • 與聊天機器人的差別：聊天機器人多半一問一答；Agent 會連續多步行動、使用工具並根據環境回饋修正。 S1S2
聊天機器人一問 → 一答
WorkflowA → B → C（路徑寫死）
Agent想 → 做 → 看 → 再想…（模型決定）

01 · 定義

自主程度是一條光譜

  • 先找最簡單的解法，只在必要時增加複雜度；很多情況下，單次 LLM 呼叫加上檢索與範例就夠了。 S1
  • Agent 會帶來更高的延遲與成本，只有在任務開放、步驟無法事先預測時才值得使用。 S1
📖 Wiki 出處：workflows-vs-agents.md › 重點 1　definition.md › 重點 5

02 · 核心元件

核心元件：大腦 + 三種能力

  • 規劃：把大任務拆成小目標，並對過去的行動做反思與修正。 S3
  • 記憶：短期記憶是上下文（in-context）中的內容；長期記憶通常存在外部向量資料庫，需要時再檢索。 S3
  • 工具使用：呼叫外部 API 取得模型權重裡沒有的資訊，例如即時資料、程式執行、專有資料庫。 S3
📖 Wiki 出處：components.md › 重點 1、2、3、4

03 · Agent Loop

Agent 的心跳：想 → 做 → 看

  • ReAct 讓 LLM 交錯產生「推理軌跡」與「任務行動」，推理幫助擬定與更新計畫，行動則從外部取得新資訊。 S2
  • 實務上，Agent 在每一步都要從環境取得「真實狀態」（例如工具結果或程式執行結果）來判斷進度。 S1
  • 必須設定停止條件（例如最大迭代次數），避免 Agent 無限循環。 S1
📖 Wiki 出處：agent-loop.md › 重點 1、4、5

03 · Agent Loop

ReAct 實際長什麼樣子？

Thought 1: 我要找出 ReAct 論文發表在哪個會議。
Action 1: Search[ReAct Synergizing Reasoning and Acting]
Observation 1: …ICLR 2023…
Thought 2: 已找到答案。
Action 2: Finish[ICLR 2023]
  • ReAct 在知識問答（HotpotQA）與事實查核（FEVER）中透過 Wikipedia API 查資料，減少了純推理時的幻覺與錯誤傳遞。 S2
  • 在互動決策任務 ALFWorld 與 WebShop 上，ReAct 的成功率分別比模仿學習／強化學習方法高出 34% 與 10%（絕對值）。 S2

04 · 規劃

規劃：把大目標拆成小步驟

  • 思維鏈（Chain-of-Thought）：在提示中示範中間推理步驟，能顯著提升 LLM 的複雜推理能力。 S8
  • 思維樹（Tree of Thoughts）：同時探索多條推理路徑、自我評估並可回溯；在 24 點遊戲上，GPT-4 搭配 CoT 只解出 4%，ToT 達到 74%。 S9
  • 任務拆解：可以靠 LLM 提示（如「完成 X 需要哪些步驟？」）、任務專屬指令，或人類輸入來完成。 S3
方式特色適合
先規劃再執行（Plan-and-Execute）一次列出完整步驟步驟穩定的任務
邊做邊規劃（ReAct）每步依觀察重新決定資訊不完整、需探索 → 見 agent-loop
搜尋式規劃（ToT）分支、評估、回溯需要嘗試多種解法的難題
📖 Wiki 出處：planning.md › 重點 1、2、3

04 · 規劃

反思：從失敗中學習

① 嘗試任務
→
② 得到回饋
（測試失敗、評估者意見）
→
③ 用文字寫下反思
→
④ 存入記憶，下次讀取
  • Reflexion：Agent 用文字對任務回饋進行反思，把反思存進記憶，在下一次嘗試中改進，不需要更新模型權重。 S4
  • Reflexion 在 HumanEval 程式題上達到 91% pass@1，高於當時 GPT-4 的 80%。 S4
📖 Wiki 出處：planning.md › 重點 4、5

05 · 工具使用

工具：讓 Agent 從「會說」變成「會做」

  • 工具讓 LLM 取得權重裡沒有的資訊與能力，例如即時資訊、程式執行與專有資料。 S3
  • Toolformer 證明 LM 可以用自我監督的方式學會「何時呼叫哪個 API、帶什麼參數」，工具包含計算機、問答系統、搜尋引擎、翻譯與行事曆。 S6
  • Model Context Protocol（MCP）是 2024 年 11 月發布的開放標準，讓 AI 應用以統一方式連接各種資料來源與工具。 S12
📖 Wiki 出處：tool-use.md › 重點 1、2、4

05 · 工具使用

Function calling 流程與好工具設計

  1. 開發者把工具的「名稱、用途、參數格式」提供給模型。
  2. 模型判斷需要時，輸出一段結構化的工具呼叫例如 JSON。
  3. 程式真正執行工具，把結果當作 Observation 回傳給模型。
  4. 模型根據結果決定下一步。
  • 工具的定義與說明文件要像寫給新進同事一樣清楚；Anthropic 稱之為「Agent–電腦介面（ACI）」，值得投入和人機介面一樣多的心力。 S1
🛡️ 能動手就可能闖禍 → 工具權限要最小化（見「風險」）
📖 Wiki 出處：tool-use.md › 重點 3、Function calling 的流程

06 · 記憶

記憶：短期靠上下文，長期靠外部儲存

記憶類型人類類比Agent 實作
感官記憶一瞬間的印象輸入的原始內容
短期／工作記憶正在想的事上下文視窗（對話、工具結果）
長期記憶筆記本、經驗向量資料庫、檔案、摘要
  • 短期記憶＝上下文中的內容（in-context learning）；長期記憶＝存在外部（常用向量資料庫），以快速檢索取用。 S3
  • Generative Agents 用「記憶流」記錄所有經驗，依「新近度、重要性、相關性」檢索，並把記憶綜合成更高層的「反思」。 S5
  • MemGPT 借鏡作業系統的分層記憶，在有限的主上下文與外部儲存之間搬移資料，讓 LLM 處理超出上下文長度的內容。 S7
📖 Wiki 出處：memory.md › 重點 1、2、3

07 · 設計模式

不一定要 Agent：五種常見模式

提示鏈
  • 提示鏈（Prompt chaining）：把任務拆成固定的連續步驟，每一步處理上一步的輸出，中間可加檢查關卡。 S1
路由
  • 路由（Routing）：先分類輸入，再交給專門的後續流程處理。 S1
平行化
  • 平行化（Parallelization）：把任務切段同時處理（分段），或同一任務跑多次再投票（投票）。 S1
協調者－工作者
  • 協調者－工作者（Orchestrator-workers）：中央 LLM 動態拆解任務、分派給工作者 LLM，再整合結果。 S1
評估者－最佳化者
  • 評估者－最佳化者（Evaluator-optimizer）：一個 LLM 產生答案，另一個 LLM 評估並給回饋，反覆迭代。 S1
📖 Wiki 出處：workflows-vs-agents.md › 重點 2、3、4、5、6

07 · 設計模式

什麼時候該用 Agent？

任務步驟能事先寫死嗎？
 ├─ 能 → 用 Workflow（提示鏈／路由／平行化）
 └─ 不能，需要依結果決定下一步
       ├─ 有明確評估標準 → 評估者－最佳化者
       ├─ 子任務無法預先知道 → 協調者－工作者
       └─ 開放式、多步、需工具 → Agent（Agent 迴圈）
Workflow ＝ 圖（graph）節點與邊由開發者事先定義
Agent ＝ 迴圈（loop）每一輪由模型決定下一個動作
實務常是混合外層是圖，某些節點內部是 Agent 迴圈
📖 Wiki 出處：workflows-vs-agents.md › 重點 決策指南、Graph 與 Loop

08 · 多代理人

多代理人：分工、對話、互相檢查

  • AutoGen 讓多個可對話的 Agent 透過互相傳訊合作完成任務，Agent 可結合 LLM、人類輸入與工具。 S10
  • Generative Agents 在沙盒小鎮中放入 25 個 Agent，它們會自發地互相傳遞消息、結交朋友並協調活動（例如籌辦情人節派對）。 S5
  • 協調者－工作者模式中，中央 LLM 動態拆解任務並分派給多個工作者，是常見的多代理人架構。 S1
架構說明例子
協調者－工作者一個主管 Agent 分派、彙整研究助理派出多個搜尋 Agent
角色分工對話每個 Agent 有固定角色互相對話「寫程式」與「審程式」兩個 Agent
辯論／投票多個 Agent 各自作答後比較對同一題取多數決（對應 workflows-vs-agents 的投票）
📖 Wiki 出處：multi-agent.md › 重點 1、2、3

09 · 評估

評估：不只看答案，要看有沒有真的做完

2,294
SWE-bench 題目數
1.96%
發表時最佳模型解題率
  • SWE-bench 從 12 個熱門 Python 專案的真實 GitHub issue 與 PR 中整理出 2,294 個題目，要求模型修改程式碼來解決問題。 S11
  • SWE-bench 發表時，表現最好的 Claude 2 只解出 1.96% 的題目，顯示真實軟體任務對 Agent 仍然困難。 S11
  • 部署前應在沙盒環境中大量測試，並設置適當的防護機制。 S1
  • 能以客觀方式驗證結果的任務（例如程式可以跑測試）特別適合 Agent，因為回饋可以直接用來迭代。 S1

10 · 風險與防護

風險：能自主行動，代價也更高

  • 提示注入（Prompt Injection）名列 OWASP LLM 應用十大風險第一名（LLM01），惡意指令可能藏在 Agent 讀到的網頁或文件中。 S13
  • 過度授權（Excessive Agency，LLM06）：給 Agent 過多功能、權限或自主性，可能導致有害的行動。 S13
  • 無上限消耗（Unbounded Consumption，LLM10）：缺乏限制時，迴圈或大量請求可能造成成本與資源失控。 S13
  • Agent 的自主性意味著更高成本與錯誤累積的可能，需在沙盒中測試並設置防護。 S1
  • 對重要步驟設置人類檢查點，讓 Agent 在關鍵時刻暫停並取得人類回饋。 S1
📖 Wiki 出處：risks.md › 重點 1、2、3、4、5

總結

帶走三件事

  1. Agent 是能感知環境並採取行動以達成目標的系統；LLM Agent 則是由大型語言模型「自己決定流程與工具使用」的系統。
  2. Agent 的核心是一個迴圈：思考（Thought）→ 行動（Action）→ 觀察（Observation），重複直到完成或觸發停止條件。
  3. 不是所有 LLM 應用都需要 Agent。先用最簡單的方案，只有在真的需要時才增加複雜度。
